About Automation with Faultwise Consulting

Does your test report look like this?

A list of red failures, and the same question for every one of them: is the product broken, or is the test? Answering it means opening the error, then the test, then the code, one failure at a time. By the time someone is done, the developers have moved on.

I built Faultwise to answer that question. It reads each failed test together with your code, tells you which failures are real bugs and how to fix them, and repairs the tests that are simply wrong.

What it does

  • Real bugs get a severity, the root cause, the evidence and a suggested fix, ready to become a ticket.
  • Broken tests get a corrected version that is run again to prove it works. A person reviews it before anything changes.
  • Problems in the environment are called out separately, so nobody chases a bug that isn't there.

Where it fits

Faultwise reads Playwright results and JUnit XML, which almost every test framework can write: web, mobile, desktop and server tests, from pytest and JUnit to Appium and Espresso. It runs in your own CI as a command or a GitHub Action, and works with Claude, a local model, or any OpenAI-compatible service. If your code can't leave the company, it doesn't have to.

How accurate is it?

I don't want you to take that on trust, so I measure it. On my demo project it classified all 23 failures correctly. In a harder benchmark of 115 generated failures designed to look like the other kind of problem, it got every one right when it could read the application code.

Before you commit, I run it on your own recent failures and we compare its verdicts with your team's. Then you know how it does on your tests, not mine.
